# Measuring what open-model inference actually costs

### Three things the field repeats that the data does not support

**Hariprasad Sudharshan** · August 2026 · Working paper **v2** · [opentoken](https://tokencalci.onrender.com)

---

## Abstract

I built a calculator to price self-hosting an open-weight model against renting the same weights from a neocloud API. It told me that running a dense model yourself costs **4 to 6 times** what a provider charges. I published that figure. Then I measured it properly and it was wrong — my fleet-sizing had assumed adding GPUs adds throughput, which is not true.

v1 of this paper was the correction. A round of external review found that the correction had its own error, of the same family : I replaced one wrong number with a **floor** and then quoted the floor as if it were a **cost**. This version separates them, and the separation turns out to be the most interesting result here.

Priced at the precision providers actually serve, across five representative models :

- **bare compute runs 0.15× to 1.80×** the neocloud rate — for four of five models, the silicon is *cheaper* than renting
- **the fully loaded cost runs 1.7× to 8.2×** — the same fleet, with idle time, people and overhead put back

**The gap is not the silicon. It is everything wrapped around the silicon.** That is a sharper version of the thing I set out to argue than the one I had.

Two further measurements, both revised downward under review :

1. **Per-model prices are not falling fast.** A fixed basket of 19 models moved between **0.976×/year and 0.840×/year** over 18 months depending on the index formula — I reported only the flattering one in v1. Under any of the three, the widely-repeated "inference falls ~10×/year" does not hold for a model you have already chosen.
2. **Tensor parallelism buys capacity, not speed.** This is a **modelling assumption that fits my data, not a measurement** — v1 called it measured, which it is not. Section 4 states what would falsify it and what it costs to settle.

Every figure below is regenerated by one committed script against pinned snapshots. Method is in section 2, limitations in section 7, and I would rather be corrected than cited.

**Disclosure :** No funding, no sponsorship, no commercial relationship with any provider named here. The paper argues for renting inference, which is a vendor-shaped conclusion, so it matters that every number I have revised has moved **against** my own prior position — twice now.

---

## 1. Why bother measuring this

Every time a lab publishes weights, the discussion moves from frontier to open as though the hard part had shipped. What shipped is the weights.

An open weight is a file. A served token is a system. Between them sit roughly ten blocks — precision, KV cache, batching, kernels, parallelism, fleet, reliability, economics, API surface — and exactly one of them arrives in the download.

We have been here before. In 2008 we had the source code and thought we had the product. It took most of a decade to name the missing work DevOps, and only after naming it did anyone budget for it. Model serving is at that stage now.

The question I wanted answered was narrow and arithmetic : **for a given open model and a given workload, what does it cost to serve yourself versus to rent, and where exactly does the difference come from.**

---

## 2. Method

Four data layers, each graded by how directly the claim traces to a record. The grades matter more than the numbers, so they are stated on every figure the tool reports.

**Model prices — measured.** LiteLLM's `model_prices_and_context_window.json`, fetched server-side, ~2,300 keys. Each catalog model is matched against every provider serving it and the **median** taken; the full min/median/max spread is retained and displayed.

> *Correction from v1 :* the median is over feed **keys**, not distinct providers. **27 of 37** comparable models carry more keys than providers (265 keys across 164 providers), so a provider that publishes several aliases is over-weighted. This is a real defect. It is disclosed rather than fixed because fixing it changes the price series, and I would rather publish the flaw now than a quietly-revised series later.

**Serving precision — observed.** The precision each model is *actually served at*, taken from per-provider quantisation in the weekly OpenRouter snapshot, modal across providers, requiring at least three reporting providers and a clear plurality before claiming to have observed anything. Where the sample is thin it falls back to the model card, then to a release-generation guess — and the basis travels with the value.

> This layer is new in v2 and it matters more than its size suggests. v1 priced every model at **fp16**. Almost nobody serves fp16, and several models in the catalogue were never released in it — so v1 charged models for twenty GPUs that had been deliberately engineered to fit one.

**Price history — derived.** Historical commits of the LiteLLM file, recovered from git, normalised through the identical code path so a point in the series means what today's number means. 19 monthly observations, 2025-01-13 to 2026-07-14.

**GPU rental — measured, with a caveat that runs against me.** Vast.ai public marketplace, per-GPU-hour min/median/max across currently-rentable offers. This is community/spot supply with no SLA — cheaper than contracted enterprise capacity that a regulated buyer could actually purchase. **So every self-host figure here is a lower bound**, and the real gap for such a buyer is wider than reported.

**Throughput — published, not measured.** Third-party vLLM and SGLang serving benchmarks (256 concurrent, 512 in / 512 out) across A100/H100/H200/B200 and 3B–70B active parameters. **These are benchmarks other people ran** — see section 4 for what that costs the argument.

The economic model rests on one asymmetry. Self-hosting is a **fixed** cost: you provision for peak and pay 24×7 whether tokens flow or not. An API is **variable**: you pay per token and idle is free. So the deciding variable is the duty cycle, and a workload stated as requests-per-day converts to peak-and-duty exactly, since duty = 1 / peak-to-average ratio.

## 3. Finding one : per-model prices are flat, but how flat depends on the formula

Two different things get called "the price falling" and they differ by roughly 20×.

**Fixed basket.** Track the same 19 models present at both ends of the window :

| Index | 18-month total | Annualised |
|---|---|---|
| Carli — arithmetic mean of price relatives *(v1 reported only this)* | 0.964× | **0.976×/yr** |
| Jevons — geometric mean | 0.770× | **0.840×/yr** |
| Median relative | 1.000× | **1.000×/yr** |

**Whats the use of showing three :**

v1 said "essentially flat" and quoted 0.976. That number is the **Carli index**, which has a documented upward bias and fails the time-reversal test — statistical agencies moved off it for exactly this reason. My basket is the shape that maximises that bias : two models fell 8–11× and are floored at zero in an arithmetic mean, two doubled and are unbounded above.

Under Jevons the same data says −16%/year, which is not "essentially flat". I did not choose Carli to flatter the result — I chose it without knowing there was a choice, which is worse and is the more common failure.

**What survives all three :** nothing resembling 10×/year. The claim the field repeats is wrong under every estimator, and that is the finding. The magnitude is not.

**Cheapest available.** The lowest-priced model in the catalog fell from **$0.100 to $0.040** per million input tokens, about **46%/year** — though this is the minimum of a *growing* set, which is monotonically non-increasing by construction, and the entire move is one step in September 2025. Treat it as a direction, not a rate.

Both series are true and answer different questions. Prices fall because *cheaper new models keep arriving*, not because the model you picked gets cheaper. If you commit to one model the API side will not drift away from you the way the folklore implies. If you re-platform to whatever is cheapest each quarter you capture the fast rate — and re-platforming is engineering work nobody costs.

**A caveat that may be fatal to the magnitude.** The basket is fixed in model identity, not in sampling frame. Provider observations inside it grew **46 → 141** over the window. Split the basket : models that gained ≥3× providers have a geomean relative of **0.404**; models with stable provider counts, **1.038**. The series sorts on *how many cheap listings entered each model's median window*, not on price. I do not think this overturns the direction. I do think it means the number is measuring something other than what I claimed, and a corrected version needs a provider-fixed-effects treatment I have not built.

I have not found this series published elsewhere. It is 73KB of JSON and the script that rebuilds it is 146 lines.

## 4. Finding two : tensor parallelism buys capacity, not speed

This is the one that invalidated my own headline number, and it is also the weakest-evidenced claim in the paper. Both things are true at once.

Total fleet throughput barely moves with GPU count :

| Model | Active | GPUs | Total tok/s |
|---|---|---|---|
| Qwen3 30B-A3B | 3B | 1 | 3,900 |
| Gemma 4 31B | 31B | 1 | 3,100 |
| Mistral Small 24B | 24B | 2 | 3,400 |
| Llama 3.3 70B | 70B | 8 | 2,800 |

Eight GPUs do not deliver eight times the tokens. They deliver roughly what one does, because tensor-parallel decode pays collective communication on every layer and that cost cancels the bandwidth added. **You split a model across GPUs to make it fit, not to make it fast.** To serve more tokens you deploy another full replica and pay for it again.

My original model grew a single fleet until it was fast enough — silently assuming width bought speed — and so demanded roughly 2.4× the hardware a workload actually needs. That is where the missing 4–6× lived.

### 4.1 What is wrong with the evidence for it

v1 presented this as measured. **It is not, and I should not have said so.** Review found three problems and all three stand :

**The four anchors are confounded by construction.** Model size and GPU count move together — the small models are the one-GPU rows and the big model is the eight-GPU row. There is no anchor anywhere in the set that varies GPU count while holding model and precision fixed, which is the only experiment that tests the claim. Attributing the decline entirely to active parameters and none to TP degree fits; so does the opposite attribution. Four points cannot separate them.

**A constant fits nearly as well.** Predicting a flat 3,275 tok/s for every row scores 1.11 geometric-mean error. My two-parameter fit scores 1.02. Two free parameters buy eight percentage points on four points spanning 2,800–3,900.

**The only same-model GPU-count comparison in the data contradicts the claim, and it is the row I excluded.** Llama 3.1 70B at fp8 on **one** H100 : 460 tok/s observed, 5,603 predicted — a **12.2× miss**. I set it aside as a different harness and batch size, which is a real confound and is not 12× wide. Discount naively for the 4× batch difference and one GPU still lands near 1,840 against 5,600 for eight — sub-linear scaling, not flat.

### 4.2 Reporting the fit honestly

v1 claimed "9 of 10 published benchmarks at geometric-mean error 1.054×". That is arithmetically true and rhetorically false, because five of those nine are the points the parameters were fitted on and score 1.000 by construction. Regenerated with the roles marked :

| Points | n | Geomean error |
|---|---|---|
| Fit points (algebraic identities, not predictions) | 4 | 1.000× |
| **Genuinely held out**, excluding the declared large-MoE blind spot | **5** | **1.099×** |
| Held out, including it | 6 | 1.414× |
| Excluded : large MoE (DeepSeek V3) | 1 | 4.99× |
| Excluded : cross-harness, batch 64, 1 GPU | 1 | **12.18×** |

Worst held-out residual is A100 at **1.38×** — Ampere has no FP8 tensor cores, so that error is architecture, not bandwidth, and the model has no term for it. The bandwidth exponent itself is fitted on **one pair** (B200/H100); pairwise exponents across the four cards span 0.699–1.396.

**So : n = 5 held out, 1.099×.** Not nine at 1.054×.

**What would settle it :** one model, one precision, tensor-parallel degrees 1 / 2 / 4 / 8, identical hardware and batch size, with the interconnect topology recorded. That is about $5 of rented H100 time. Until it exists this section is a modelling assumption that fits the available data, and the tool now says so.

### 4.3 The Tensor Parallel Tax, and its domain

It produces a single number you can compute before committing a quarter. I am naming it because unnamed things do not get budgeted.

> **TPT — Tensor Parallel Tax**
> TPT = ceil( (total params × bytes per param × 1.3) / GPU VRAM )
> The GPUs one replica needs, purely to hold the model.

**Where the 1.3 comes from, and where it fails.** It is a flat 30% allowance for KV cache and activations. It reads no context length, no batch size, no concurrency and no attention architecture, and `ctx` values in the catalogue span 4K to 10M without touching it.

At the benchmark configuration these numbers are fitted to — 1K sequence, 256 concurrent, 70B with GQA — the required headroom is about **1.61×**, not 1.30. So **TPT is wrong at its own anchor configuration**, and at production context lengths it is wrong by an order of magnitude.

Worse, and this one I would have caught if I had looked : because the allowance is a fraction of *weight bytes*, quantising a model **shrinks** its KV budget. gpt-oss-120b is credited with 71 GB of headroom at fp16 and 19 GB at int4 — the inverse of why anyone quantises. Every "self-host wins once you quantise" verdict in the tool is therefore computed on a fleet that could not hold the concurrency it is credited with.

**TPT as published is a weights-fit formula.** It is useful as that, it is not a capacity model, and the name over-claims. A defensible version needs a KV term — `f(ctx, concurrency, kv_heads, head_dim, precision)` — and the inputs are already in the catalogue. Until that lands, read TPT as "how many cards to hold the weights" and nothing more.

## 5. Finding three : the cost multiple, floor and loaded

This replaces v1's single-number claim, which conflated two quantities.

Priced at the precision providers actually serve, at 200,000 requests/day of 2,000 in / 500 out on business-hours traffic (33% duty), H100s, three-year amortisation :

| Model | Served at | TPT | Fleet | Bare compute | Loaded |
|---|---|---|---|---|---|
| gpt-oss-120b | int4 | 1× | 2 | **0.15×** | 1.7× |
| Qwen3 30B-A3B | fp8 | 1× | 3 | **0.26×** | 2.6× |
| Gemma 4 31B | fp16 | 2× | 12 | **0.49×** | 2.5× |
| Llama 3.3 70B | fp8 | 2× | 8 | **0.54×** | 3.7× |
| DeepSeek V3.2 | fp8 | 11× | 33 | **1.80×** | 8.2× |

**Bare compute** is the GPU line alone, at 100% utilisation, nobody paid, no overhead, no idle. **Loaded** is what you actually pay at this workload. v1 quoted the first and called it the second.

**Two things follow, and the second is the paper's real result.**

*First, precision decides the fleet.* The same table at fp16 — the precision v1 used throughout — reads 4× TPT and 8.7× loaded for gpt-oss-120b, and 22× TPT and 30.9× loaded for DeepSeek. Scoring a model at a precision it was never released in punishes exactly the quantisation-aware work that gets it under a VRAM boundary. gpt-oss ships MXFP4 and was engineered to fit one 80GB card; v1 demanded twenty.

*Second, and this is the finding : the silicon is not the problem.* For four of five models bare compute is **cheaper** than renting. The premium is created almost entirely by what surrounds it — idle capacity, staffing, overhead, redundancy. A provider is not beating you on kernels. They are beating you on **pooling uncorrelated demand across thousands of customers**, which is a property of their customer base and not of their engineering.

That is a better statement of "open weights are not open inference" than the one I published. The missing decade is not silicon and not even mostly software. It is the operational and demand-shaped layer that a download cannot contain.

## 6. Finding four : price dispersion, and what cross-feed disagreement is really measuring

v1 claimed "two independent price feeds disagree on 22% of models, worst 5.7×". Regenerated, and with the checks I should have run first :

| | |
|---|---|
| Comparable models | 37 |
| Disagree by more than 1.5× | **7 (19%)**, worst Mistral NeMo at 5.00× |
| **Thin on one side (n ≤ 2)** | **21 of 37** |
| **LiteLLM medians containing an OpenRouter row** | **10 of 37** |

Both caveats cut against the claim and neither was in v1.

**The feeds are not independent.** OpenRouter is itself one of the providers inside the LiteLLM median for 10 of these models. Comparing a feed against a feed that partly contains it is not an independence test, and I should withdraw the word.

**Most of the "disagreement" is sample size.** With 21 of 37 models thin on one side, comparing a single observation against a median of eighteen produces divergence that says nothing about the market.

**What survives, and it is worth keeping :** the *dispersion within a single model* is enormous and well-sampled. DeepSeek V3.2 spans **$0.14 to $3.00** per million input tokens across 39 listings from 13 providers — a 21× range. Llama 3.3 70B ranged $0.12–$0.90 across 13 listings from 11 providers. That is not a feed artefact; it is the market.

So the defensible version of finding three is not "two feeds disagree". It is: **any single-source price table reports one sample as if it were the market, and the spread it hides is wider than any modelling choice in this paper.** Which provider you pick moves the answer more than fleet sizing, precision, or duty cycle. Most calculators in this space, including mine until recently, quote a point estimate.

There is a further wrinkle that makes cross-model comparison harder than it looks, and it is why section 2's serving-precision layer exists : providers serve the *same* model at fp4 through fp16, so a cheap listing may simply be a heavily quantised one.

## 7. What this implies, briefly

Self-hosting loses on **loaded** cost for every model in the table above, by 1.7× to 8.2×. It loses least where the model fits in one card and most where it needs eleven. On **bare compute** it usually wins, which is the whole point of section 5.

The two blocks that dominate the gap are not engineering skill. They are **idle capacity** — you provision for peak, a provider pools demand across thousands of uncorrelated customers — and **staffing**, where a single inference engineer costs more per year than the hardware underneath them.

So the intermediate position is straightforward. Rent while you learn the shape of your demand, measure your real duty cycle, and revisit with data instead of a spreadsheet. The door does not close — weights you can download today you can still download in eighteen months, on cheaper hardware, with a faster serving stack.

One correction to the *non*-cost argument as well : "our data cannot leave" is now largely satisfiable contractually. Zero Data Retention is widely available at no per-token premium. There is a ladder — standard API, ZDR, in-region provider, dedicated endpoint, own hardware — and most discussions jump from the first rung to the last, skipping three cheaper options. The last rung is a **physical** guarantee where the others are **contractual** ones. Sometimes a regulator demands exactly that. Often nobody has written down which requirement actually binds.

## 8. Limitations

Stated before the reproduction section on purpose, because these are the places I expect to be corrected. Several of these are new in v2 and came from reviewers, not from me.

**The throughput data is second-hand and thinly held out.** Ten of eleven anchors come from one published benchmark run. n = 5 genuinely held out. Renting an H100 for two hours costs about $5 and would move this layer from `published` to `measured`. That is the single highest-value thing left undone and section 4.1 says exactly which experiment to run.

**The parallelism finding is an assumption, not a measurement.** See 4.1. v1 said otherwise.

**TPT omits KV cache and is wrong at its own anchor.** See 4.3.

**Throughput swings ~100× with batch size** and the model has no batch term — every figure assumes a throughput-optimised configuration at high concurrency, which is a demand-density assumption, not a hardware property. At low concurrency the self-hosting case is *worse* than reported.

**Serving precision is observed for some models and guessed for others.** Where fewer than three providers report a precision, the value falls back to a model card or a release-generation heuristic. Precision compounds — up to 4× on weight bytes and up to 3× on throughput — so this is a load-bearing input with uneven provenance. Corrections to that table are the cheapest useful contribution anyone can make here.

**The price median is over feed keys, not providers.** See section 2. 27 of 37 models are affected.

**The basket's sampling frame is not fixed.** See section 3. This may be fatal to the *magnitude* of finding one.

**Prices are published list prices.** Negotiated enterprise rates, committed-use discounts and free tiers are excluded, and all three favour the buyer — i.e. against self-hosting.

**GPU rental is spot-market supply.** Community capacity with no SLA, cheaper than anything a regulated buyer could contract. Every self-host figure is a lower bound.

**Some neocloud pricing is probably below cost.** Nothing in public data separates a subsidised price from an efficient one. If today's cheapest listings are land-grab pricing, every break-even moves toward self-hosting when that stops.

**The model prices only one axis.** No fine-tuning, no multi-LoRA serving — dozens of adapters on one resident base model, which does not exist on a per-token API at any price and is the most common real reason teams self-host. No latency SLO, no p95, no TTFT. No prefix caching or offline batch scheduling on the self-host side, while the API side gets prompt caching and batch discounts — that ledger is one-sided and it favours renting.

**The capability tier is editorial.** The coarse 1–4 quality rating is my judgement, not a benchmark score.

**The GPU set is NVIDIA-only.** No MI300X, Gaudi or TPU — accelerators whose commercial pitch is precisely open-model serving economics.

## 9. Reproduce it

Everything is a committed file or a re-runnable script. New in v2 : the paper's own tables regenerate from one command against pinned snapshots, so a reader can check the figures rather than trust them.

```
git clone https://github.com/brettleehari/tokencalci
npm install

npm run paper:figures        # regenerates every table in this paper
npm run paper:figures -- --live   # same, against today's live feeds instead
npm run refresh:history      # rebuild the 19-point price series from git
npm start                    # the calculator, with every input graded
```

`npm run paper:figures` prints the exact configuration it used — workload, duty cycle, GPU price and basis, amortisation, staffing, overhead — before any table. If a number here does not match what that script prints, the paper is wrong and I would like to know.

- `scripts/paper-figures.mjs` — regenerates sections 3, 4.2, 5 and 6
- `server/paper-prices.json`, `server/paper-gpu-prices.json` — the pinned feed state these tables were computed from
- `server/price-history.json` — the price series, 19 points
- `server/backfill-history.js` — recovers it from LiteLLM's git history
- `client/src/throughput.js` — the benchmark anchors and the fitted scaling factors
- `GET /api/sources` — every data layer with its source, cadence, confidence grade and limitations

If a number here is wrong I would rather find out from you than from a reader six months from now.
